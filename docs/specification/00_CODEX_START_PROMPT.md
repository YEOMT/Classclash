# 클래스 클래시 첫 플레이 가능 버전 구현 지시

아래 본문을 Codex의 작업 지시로 사용한다.

---

YEOMT/Classclash 저장소에서 학습용 자동 전투 게임 **클래스 클래시 Class Clash**의 첫 플레이 가능 버전을 구현하라. docs/specification의 모든 문서를 먼저 읽고, 기존 AGENTS.md·소스·패키지·테스트·git 상태를 확인하라. 이 문서는 구현 계획만 요구하는 것이 아니다. 설치 후 실제로 방을 만들고, 학생 또는 AI가 참가하여, 퀴즈로 자원을 얻고, 영웅을 출정시키고, 넥서스를 파괴한 뒤 시상식과 재경기까지 진행되는 게임을 완성해야 한다.

다음 사용자 확정 요구를 변경하지 마라.

- 2진영, 상·하 2라인, 좌우 끝 넥서스. 팀당 각 라인 일반 타워 2개와 넥서스 수호 타워 2개. 넓은 두 길은 수호 타워 전방에서 자연스럽게 합쳐진다.
- 최대 30명, 플레이어별 동시 출정 영웅 1명. 출정한 영웅은 완전 자동 전투한다. 생존 중 조작·라인 변경·교체·성장 적용·뽑기를 할 수 없고, 퀴즈로 자원은 얻을 수 있다.
- 사망하면 정비 UI가 열린다. 보유 영웅 그대로 출정, 교체, 레벨업, 강화, 뽑기, 가능한 퀴즈, 출정 라인 선택을 수행한다. 자동으로 부활시키지 않는다. 플레이어가 출정 버튼을 누르면 본진에서 다시 출발한다.
- 시작 전 퀴즈 20문제로 초기 자산을 얻는다. 전투 중 퀴즈는 한 묶음 10문제, 10번째 답안 확정 후 30초 쿨타임. 전투는 문제 풀이 중에도 계속된다.
- 일반 뽑기권 2원, 고급 뽑기권 10원. 전설은 고급 뽑기에서만 10%. 전설 영웅은 룬 마법사, 고대의 존재, 수호령의 3명이다. 기타 확률과 보상 단가는 명세의 초기 설정을 사용한다.
- 영웅마다 성장과 강화가 독립적이며 교체 시 옮겨지지 않는다. 최고 레벨의 스킬은 정확히 2개다.
- 미니언은 팀·라인마다 근접 3기, 원거리 4기. 경기 시작에 첫 웨이브가 생성된다.
- 호스트는 스코어판과 전체 맵을 고정 화면으로 보고, 모든 실제 공격·투사체·스킬·피격 이펙트를 볼 수 있어야 한다. 학생은 자신의 영웅을 따라가는 카메라를 사용한다.
- 경기 길이의 목표는 10~13분이며 승리는 적 넥서스 파괴다. 임의로 13분 체력 비교 승리로 바꾸지 않는다.
- 호스트가 로비에서 AI 학생을 추가·제거·팀 배치하고 30명을 채울 수 있어야 한다. 사람 0명·AI 30명, 사람 1명·AI 29명으로도 전체 흐름이 작동한다.
- 픽셀 그래픽과 애니메이션의 가독성·타격감이 핵심이다. 18명 모두 독자적 외형과 2개 스킬을 구현한다. 공식 Teamfight Manager 자료에서 역할과 액션의 명료함을 참고하되 원작 자산을 복제하지 않는다.

구현 지침:

1. 모듈별 책임을 나누되 문서 정리로 종료하지 마라. Node.js 권위 서버, TypeScript 공용 모델, PixiJS 전장 렌더링, HTML 기반 호스트·학생 UI를 연결하라. 기본 실행은 외부 유료 서비스 가입 없이 로컬에서 가능해야 한다.
2. 룸·경기·플레이어·영웅 인스턴스·퀴즈 시도·요청·이벤트의 ID를 분리하라. 자원·확률·채점·전투·승패·시상은 서버가 결정한다. 학생 브라우저가 돈·정답·피해·승패를 정하지 못하게 하라.
3. 먼저 전체 수업 흐름이 도는 최소 연결을 만들고, 동일 코드에 18명 영웅과 정식 도트 액션을 완성하라. 테스트용 임시 그림이나 전투 계산을 최종본으로 남기지 마라.
4. docs/specification/02의 이동·진형·사거리·공성 규칙, 03의 스킬 발동 조건과 히트 프레임을 실제로 구현하라. 후방 캐릭터도 이유 있게 움직이고, 근접이 뭉쳐 서 있거나 포탑 앞에서 떨지 않게 하라.
5. docs/specification/05의 인수 조건을 실행 가능한 테스트와 수동 시각 검토로 연결하라. 단순 정적 문법 검사만 하고 정상 작동이라고 보고하지 마라.
6. install, dev, build, start, typecheck, test, test:e2e, test:load, test:soak 실행 방법을 README에 제공하라. 테스트는 실패 시 비정상 종료 코드를 반환해야 한다.
7. 빈 저장소면 프로젝트를 초기화한다. 원격에 새 파일이 생겼다면 기존 작업을 보존하고 별도 작업 브랜치로 통합한다. 사용자 요청 없는 강제 push나 기존 코드 전체 삭제를 하지 마라.
8. 공개 배포 자격 증명이나 실기기가 없으면 그 검증만 미완료로 표시하고, 로컬 실행·서버·봇·브라우저 검증은 가능한 범위에서 끝내라. GitHub Pages만으로 실시간 게임 서버가 생긴 것처럼 설명하지 마라.
9. 미확정 수치는 명세의 초기값으로 진행한다. 사소한 선택 때문에 질문하며 작업을 멈추지 않는다. 수치 조정은 balance 설정과 CHANGELOG에 남긴다. 사용자 확정 규칙을 바꿔야 할 충돌만 구체적으로 보고한다.
10. 작업이 여러 세션에 걸리면 PROGRESS.md에 현재 커밋·완료 기능·남은 실패·다음 실행 명령을 남기고 이어서 진행한다. 완성 범위를 조용히 축소하지 않는다.

완료 시 제출물:

- 실제 실행 가능한 전체 프로젝트와 고정 의존성 파일.
- 로컬 시작 방법과 호스트·학생 테스트 방법.
- 18명 영웅의 도트 자산·애니메이션·스킬 정의와 출처/제작 상태.
- 호스트 로비 AI 추가 기능, 30 AI 경기, 사람 1+AI 29 경기의 실제 결과.
- 주요 화면 캡처와 전투 동영상 또는 재현 가능한 시각 점검 기록.
- 3회 연속 재경기, 새로고침·재접속, 중복 요청, 퀴즈 중 사망, 전체 시상식에 대한 검증 결과.
- 30 표준 AI의 경기 길이 분포와 패스·실패·미실행이 구분된 TEST_REPORT.md.
- 알려진 제한, 실제 배포 여부, 실제 학교 기기 검증 여부.

다음은 완료로 인정하지 않는다: 버튼만 있는 목업, 가짜 전투 재생, 이름만 다른 동일 영웅, 모든 스킬을 같은 원형 폭발로 표현한 버전, 영웅 6명만 구현한 버전, 학생 돈을 클라이언트가 직접 늘리는 구조, 봇에만 무제한 자원을 주는 구조, 화면이 비어도 콘솔 오류가 없다는 이유로 성공 처리한 결과, 미실행 테스트를 통과로 적은 보고서.
