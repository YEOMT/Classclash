# 04. 실시간 통신·저장·보안·공개 배포

## 1. 기존 기술 구조 보존

원격 조사 기준은 Node 24 계열, TypeScript, WebSocket(ws), SQLite WAL, PixiJS 8, Vite/HTML UI다. `package-lock.json`과 현재 정상 실행 환경을 먼저 재현한다. 이번 작업을 계기로 런타임·렌더러·DB를 모두 새 제품으로 바꾸지 않는다.

Node 서버가 정적 클라이언트와 `/ws`를 같은 origin에서 제공하는 현재 구조를 우선한다. GitHub에 코드가 올라간 것, main에 병합된 것, 온라인 서버가 새 커밋을 실행하는 것은 별개 상태다.

GitHub Pages는 정적 호스팅이므로 현재 Node 전투 서버를 대신할 수 없다.[S3] Pages를 쓰는 경우 게임 서버는 별도이며 연결 설정·origin·실제 동작을 검증해야 한다. 초기 배포는 프런트·API·WS를 같은 도메인으로 제공해 불필요한 복잡도를 줄인다.

## 2. 단일 권위와 처리 주기

현행 기본: 고정 틱 20Hz, AI 전술 5Hz, 스냅샷 10Hz, 클라이언트 60fps 목표. 목표값이지 이번 문서 작성 과정에서 측정한 성능이 아니다.

클라이언트는 사용자 의도를 보내고 서버 결과를 표시한다. 이동·투사체·피해를 클라이언트가 독립 재계산해 다른 전투를 만들지 않는다. 카메라·프레임·장식 입자는 로컬 처리할 수 있다.

브라우저가 숨김 탭이 되어 렌더링이 멈춰도 서버 전투는 계속된다. 복귀 때 오래된 장면을 빠르게 모두 재생하지 말고 최신 상태와 아직 유효한 효과로 복원한다.

## 3. 스냅샷·액션·이벤트 계약

### 3.1 상태와 사건을 구분

상태: 위치·체력·현재 액션·상태이상·구조물·활성 투사체·활성 지속효과.
사건: 공격 시작/발사/적중/취소, 단발 치유·보호막 부여, 죽음, 구조물 파괴, 시상 확정.

10Hz 스냅샷 사이에서 생성·종료된 짧은 사건이 누락되지 않게 한다. 현행 이벤트 ACK·순번 재전송 기능을 보존하고, 수신·소비·실제 표시를 각각 계측한다.

권장 필드 계약은 현재 타입에 대응해 사용한다.

```text
Snapshot: matchId, protocolVersion, engineVersion, tick,
          snapshotSeq, serverTime, publicState, privatePlayerProjection
Action:   actionId, sourceEntityId, deploymentId, skillId/type,
          startTick, releaseTick, recoveryEndTick, aim, targetId, cancelTick?
Event:    eventId, eventSeq, matchId, tick, type, sourceEntityId,
          targetIds, actionId, projectileId?, position, effectId, hitIndex?
```

### 3.2 표현 시간

클라이언트는 일정한 보간 지연을 두고 서버 시간을 추정한다. 초기 버퍼 100~150ms를 비교하되 장비·회선 결과로 조정한다. 위치와 이벤트를 같은 표시 타임라인에 놓아 화살보다 먼저 피해가 보이거나 이미 죽은 영웅이 공격하는 현상을 줄인다.

장시간 미수신 시 무한 외삽하지 않는다. 짧은 유한 외삽 후 연결 상태를 표시하고 재동기화한다. 재연결로 지나간 단발 효과는 사유를 기록해 생략하고, 현재 활성 장판·보호막·투사체는 상태에서 복원한다. 이 복구 정책은 정상 접속 중 사건 유실을 정당화하지 않는다.

### 3.3 역압과 큐

느린 클라이언트 때문에 전체 서버가 멈추면 안 된다. 중간 위치 스냅샷은 오래된 것부터 합치거나 최신 것으로 교체할 수 있다. 명령 응답·경제 결과·경기 종료·필수 사건은 무조건 버리지 않는다. 큐 크기·평균 지연·압축 비용을 측정한다.

현재 full snapshot이 안정적으로 작동하면 우선 최적화한다. 대역폭 측정 없이 delta·binary 프로토콜로 전면 교체하지 않는다. 변경한다면 초기 full snapshot, baseline 확인, 누락 복구, 버전 협상 시험을 추가한다.

## 4. 서버 성능과 저장 경로

원격 PROGRESS.md에는 전체 틱 비용 p95 57.1ms/p99 132.07ms, 목표 미달이 기록되어 있다. 이는 이전 개발 보고서 값이며 이번 작성 과정에서 새로 재현한 측정이 아니다.[R4]

개선은 먼저 비용을 분리해 측정한다: AI, 경로, 충돌, 스킬/투사체, 정산, serialization, compression, DB commit/checkpoint, socket enqueue.

### 4.1 우선 최적화

- 공간 해시·주변 후보 캐시를 사용하고 전 유닛을 중첩 순회하는 경로를 줄인다.
- 역할/스킬 판단은 틱별로 분산하고 큰 사건만 즉시 무효화한다.
- 정적 지형·타워 데이터·텍스처·스킬 메타데이터를 반복 생성하지 않는다.
- 수신자마다 동일 공개 상태를 JSON으로 다시 만드는 비용을 줄이되 개인 창고/답안은 분리한다.
- 동기식 DB 체크포인트와 압축이 틱을 차단하는지 프로파일링한다.
- 병목이 확인되면 worker/단일 저장 큐로 분리하되 아래 내구성 계약을 유지한다. 무조건 모든 경로를 비동기로 바꾸지는 않는다.

### 4.2 내구성 계약

인간의 정답 보상·구매·성장·출정 확정은 요청 ID 기반으로 한 번만 커밋되고, 성공 응답은 durable commit 뒤에 보낸다. 저장 실패 시 성공 표시하지 않는다. 비동기화를 위해 먼저 ACK하고 나중에 DB에 쓰는 방식은 금지한다.

판내 지갑·보유 영웅·퀴즈 진행·쿨타임·명령 응답이 같은 확정 상태로 복원되어야 한다. 기존 1초 전투 체크포인트 복구 계약은 유지하고, 서버 중단 시 최대 손실 가능한 전투 시간과 이미 확정한 거래의 차이를 보고한다. 서버 중단 시간을 전투 시간에 더하지 않는다.

SQLite를 여러 프로세스가 임의로 같은 상태의 권위 서버로 공유하지 않는다. 초기 공개 운영은 **단일 권위 인스턴스**를 기준으로 한다. 수평 확장은 별도 설계 없이는 사용하지 않는다.

### 4.3 백업·마이그레이션

스키마·engineVersion·assetVersion·balanceVersion을 기록한다. 이전 진행 중 경기와 호환되지 않으면 삭제하지 말고 유지/복구/새 방 시작을 안전하게 안내한다. DB를 공개 저장소나 빌드 산출물에 포함하지 않는다.

실행 중인 SQLite의 메인 파일만 복사해 백업 성공으로 처리하지 않는다. SQLite의 일관된 온라인 백업 또는 적절히 정지한 스냅샷을 사용하고, 복원 검사를 한다.[S8] 백업 이름에 학생 개인정보를 넣지 않는다.

## 5. 클라이언트 렌더링 성능

PixiJS 공식 문서는 sprite sheet, batching, 매 프레임 바뀌는 텍스트·복잡한 Graphics·많은 filter의 비용을 설명한다.[S7] 다음은 이 프로젝트의 적용 지침이다.

- 정적 지형은 사전 패킹한 텍스처/타일 청크로 처리한다. 매 프레임 procedural 지형을 다시 그리지 않는다.
- 공통 texture/atlas를 공유하고 무분별한 Sprite 생성·파기를 피한다.
- 필수 투사체·장판은 의미를 유지한 최저비용 형태로 표현한다. 장식 입자를 먼저 줄인다.
- HP/이름/수치는 실제 값이 바뀔 때 갱신한다. 모든 유닛의 텍스트를 매 프레임 다시 만든다거나 거대한 통계 DOM을 전장과 함께 새로 그리지 않는다.
- y 정렬·필터·blend-mode 변경 비용을 계측한다. 효과를 줄이려고 모든 캐릭터의 애니메이션을 정지시키지 않는다.
- 학생 카메라 밖의 렌더링은 culling 가능하나 서버 상태와 이벤트 원장 자체는 버리지 않는다. 호스트 전체맵에서는 두 라인 모두 보이므로 같은 이유로 한 라인 렌더링을 끄지 않는다.
- 품질 모드는 장식 밀도·배경 애니메이션·해상도 예산을 조정한다. 핵심 스킬·상태·발사체를 숨기는 모드는 금지한다.

## 6. 공개 운영 보안

공개 URL은 누구나 접속할 수 있으므로 로컬과 같은 무제한 방 생성 정책을 그대로 노출하지 않는다.

- 기존 인증을 보존하며 호스트 방 생성에는 운영자 설정 접근 코드/인증 등 최소 보호를 적용한다. 학생 회원가입을 새로 요구할 필요는 없다. 접근 코드는 서버 비밀 설정으로 보관하고 클라이언트 번들에 넣지 않는다.
- roomCode는 참가를 찾는 값이지 호스트 권한이 아니다. 호스트 세션 토큰을 QR/URL/로그에 넣지 않는다.
- WebSocket handshake/HELLO, 메시지 schema/크기/역할/단계/빈도, REST 입력을 검증한다.
- Origin allowlist와 신뢰할 reverse proxy 범위를 정한다. 외부의 임의 X-Forwarded-* 값을 그대로 신뢰하지 않는다.
- rate limit은 세션/요청 종류 중심으로 하고, 학교의 30명이 하나의 NAT IP를 쓸 수 있다는 점을 고려한다. 한 명의 정상 퀴즈 제출 때문에 학급 전체를 차단하지 않는다.
- 학생 스냅샷에 타인의 창고·지갑 상세·문제 정답·봇 예정 응답·세션 해시·서버 난수 상태를 보내지 않는다.
- nickname·문제 본문은 텍스트로 렌더링해 HTML/script 삽입을 막는다.
- 방 만료·오래된 데이터 정리·최대 활성 방 수를 설정한다. 진행 중 방을 메모리 절약 목적으로 몰래 삭제하지 않는다.
- 서버가 감당할 방 수를 측정하고 초과 방은 명시적으로 거절한다. 여러 학급 동시 사용을 검증 없이 보장하지 않는다.
- 운영 모드에서 시험 배속, 디버그 전투 조작, 미래 정답 접근 API를 닫는다.

## 7. 실제 공개 URL 배포 원칙

### 7.1 기존 주소부터 조사

Codex의 로컬 환경·README·배포 설정·접근 가능한 호스팅 서비스에서 기존 배포 origin과 상태를 먼저 확인한다. 실제 주소가 있으면 가능한 한 유지하고 갱신한다. 주소를 찾지 못했는데 임의의 `classclash...` 주소를 만들어 제시하지 않는다.

현재 문서 조사만으로 사용자의 호스팅 계정·서버·도메인·비용 승인은 확인되지 않았다. 이것은 서버가 없다는 단정이 아니다. 구현 환경에서 확인해야 한다.

### 7.2 권장 배포 형태

현재 구조에 맞는 기본 경로는 다음이다.

`브라우저 HTTPS/WSS → TLS reverse proxy 또는 호스팅 TLS → Node 앱 → 영구 로컬 볼륨의 SQLite`

이미 권한이 있는 서버가 있으면 그것을 우선한다. 서버가 없다면 지속 실행 Node/WebSocket, 영구 디스크, 공개 TLS origin을 지원하는 호스팅을 선택한다. 신규 결제·플랜 변경·도메인 구입은 승인 없이 하지 않는다.

예를 들어 Render는 WebSocket과 공개 주소를 제공하고, 영구 디스크는 유료 서비스에 연결된다. 기본 파일시스템은 재시작/배포 때 보존되지 않는다.[S4][S5] 이는 기능을 설명하는 참고 예시이며 이 프로젝트가 Render에 배포되었거나 해당 비용이 승인되었다는 뜻은 아니다.

VPS를 사용하는 경우 Caddy 같은 reverse proxy로 HTTPS와 WebSocket을 연결할 수 있다. 공인 DNS, 포트 접근, 인증서 저장을 갖춰야 하며 단순 설정 파일 작성이 공개 인증서 발급 완료를 뜻하지 않는다.[S6]

### 7.3 필수 운영 설정

- 실행 중인 앱은 `HOST=0.0.0.0`과 플랫폼의 PORT에 바인딩한다. proxy 뒤에서는 외부에 앱 포트를 직접 개방할 필요가 없는 구성을 우선한다.
- `APP_ORIGIN`은 실제 공개 HTTPS origin. 학생 링크·QR은 요청의 임의 Host가 아니라 검증된 공개 origin으로 만든다.
- 프런트 WS 주소는 실제 origin을 기준으로 `/ws`의 `wss:`를 사용한다. localhost·사설 IP를 번들에 박지 않는다.
- `DATABASE_PATH`는 영구 마운트 경로. 앱 사용자에게 쓰기 권한이 있어야 하고 재배포 후 유지되어야 한다.
- NODE_ENV는 production, 시험 배속은 비활성. 비밀 값은 CI/호스팅 secret에 보관한다.
- 프로세스 재시작 정책, 로그 rotation, 디스크/메모리 한계, 정상 종료 시 체크포인트를 준비한다.
- 장기 수업용 서비스는 수업 중 sleep이 발생하지 않는 설정을 확인한다. 무료 플랜의 제약을 확인하지 않고 '무료·항상 접속'이라고 안내하지 않는다.

### 7.4 컨테이너/CI 산출물

실제 환경에 맞는 `Dockerfile`, `.dockerignore`, 배포 manifest/compose 또는 호스팅 설정, `.env.example`, `DEPLOYMENT.md`를 작성한다. Docker는 패키지 lock을 사용하고 Node 버전 범위를 유지한다. builder에는 빌드 의존성, runtime에는 실행에 필요한 파일·의존성만 둔다. 소스 자산이 빌드 후 다시 덮어써지지 않게 한다.

CI 단계: clean install→typecheck→원본 아트 해시 검사→unit/integration→build→선택된 E2E→버전 포함 배포 아티팩트. 로컬 개발 결과가 아니라 **CI가 검증한 커밋과 자산 해시**를 배포한다.

기존 경기가 있을 때 자동 배포로 서버를 끊지 않도록 기본 정책은 새 방 생성 차단→활성 경기 종료 대기→체크포인트/백업→업데이트다. 강제 업데이트가 필요하면 호스트에게 영향을 고지하고 명시적인 운영 행동으로 실행한다. SQLite 단일 볼륨 구조에서 무중단 배포를 자동 보장하지 않는다.

## 8. 버전 확인과 캐시

`/api/health` 또는 읽기 전용 version endpoint에 appVersion, commitSha, buildTime, assetManifestHash, protocolVersion을 제공한다. 학생 데이터·비밀 환경 변수는 포함하지 않는다. UI의 설정/하단에서도 현재 버전을 확인할 수 있다.

HTML/manifest는 적절한 재검증 정책을 사용하고, 해시가 붙은 자산에는 장기 캐시를 쓸 수 있다. 새 UI가 구 엔진/구 아틀라스와 섞이면 버전 불일치 안내와 안전한 재접속/새로고침 경로를 제공한다. 진행 중 답안을 보존하지 않은 상태에서 강제 새로고침하지 않는다.

배포 성공 검증에서 Git SHA뿐 아니라 실제 스프라이트 자산 해시도 확인한다. 코드만 최신이고 오래된 PNG를 서비스하는 경우를 잡아낸다.

## 9. 외부 접속 인수 시험

다음은 배포 후 실제 공개 origin에서 실행해야 한다.

1. 외부 네트워크의 브라우저에서 HTTPS 인증서 오류 없이 진입.
2. 호스트 인증·방 생성·초대 URL·QR 생성. 링크에 localhost/토큰/사설 IP가 없음.
3. 별도 브라우저/기기에서 학생 참가, WSS 연결, 명단·팀 상태 동기화.
4. 시작 퀴즈·첫 정비·출정·전투 중 퀴즈·사망 후 수동 재출정.
5. 서버와 프런트 버전/스프라이트 해시 일치.
6. 학생 새로고침·잠깐 네트워크 차단 후 지갑·퀴즈·영웅 상태 복구.
7. 넥서스 파괴·결과·시상·재경기.
8. 분리된 시험 방에서 서버 재시작·영구 DB 복원. 운영 수업을 시험 대상으로 재시작하지 않음.

외부 독립 WS 클라이언트 부하 시험과 실제 화면 렌더링 시험은 별도다. 휴대폰·학교 Wi-Fi를 실제로 쓰지 않았다면 그 항목은 NOT_RUN이다. 배포 서버 내부에서 curl 성공한 것만으로 외부 학생 접속 성공이라고 보고하지 않는다.

## 10. 최종 제출할 배포 정보

`DEPLOYMENT_REPORT.json`과 사람이 읽는 `DEPLOYMENT.md`에 아래를 기록한다.

- 상태: PUBLIC_VERIFIED / DEPLOYED_NOT_EXTERNALLY_VERIFIED / BLOCKED_DEPLOYMENT.
- 실제 공개 플레이 URL, 실제 검증한 호스트/학생 진입 방법. 운영 활성 방의 토큰은 공개하지 않음.
- 배포 provider/region/runtime, 영구 저장소, 실행 커밋·자산 해시.
- HTTPS/WSS/health/외부참가/전체경기/재접속/영구저장 시험의 결과와 증거.
- 지원되는 동시 방·클라이언트 규모와 **측정 환경**.
- 비용 승인 여부·선택된 운영 제약. 추정 가격을 확정 청구액으로 쓰지 않음.
- 미완료이면 필요한 권한·설정·마지막 실제 오류와 완료된 부분.

주소가 미확정이면 JSON 값은 null이다. 예시 도메인, 임시 미리보기, 갤러리, GitHub 저장소 URL을 최종 플레이 주소 필드에 넣지 않는다. 공개 배포 실패를 숨기지 말고 로컬 실행 경로와 원격 반영 상태도 각각 보고한다.

## 11. GitHub 반영

로컬 최신 아트와 코드를 보존한 브랜치에 커밋하고 실제 push 성공을 확인한다. PR이 있으면 exact URL과 head SHA를 보고하고, main 병합 여부와 배포 커밋을 따로 표시한다. 사용자가 승인하지 않은 main 강제 덮어쓰기·force push·히스토리 삭제는 금지한다.

'commit 완료'는 'push 완료'가 아니며, 'push 완료'는 '배포 완료'가 아니다. GitHub 접근이 실패하면 그 원인과 보존된 로컬 커밋/패키지를 남기고 성공이라고 쓰지 않는다.
