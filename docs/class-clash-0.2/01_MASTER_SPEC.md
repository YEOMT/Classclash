# 01. 통합 마스터 명세

## 1. 목표와 완료의 의미

클래스 클래시는 최대 30명의 학생이 퀴즈로 얻은 판내 재화로 영웅을 준비하고, 두 진영의 넓은 상·하 라인에서 자동으로 싸우는 실시간 공성 게임이다. 이번 작업은 기존 시스템을 보존하면서 **그래픽, 이동과 교전의 판단, 타격과 스킬의 표현, 관전 UI, 학생 정비 UX, 실제 온라인 접속**을 하나의 일관된 제품으로 개선한다.

최종 결과는 그림만 예쁜 갤러리나 로컬 기술 데모가 아니다. 실제 학생과 AI가 로비→시작 퀴즈→첫 정비→출정→전투·퀴즈→사망·정비→재출정→넥서스 파괴→시상→재경기를 완주하고, 같은 게임이 공개 HTTPS 주소에서도 작동해야 한다. 운영 권한이 없는 경우에는 기능 구현 완료와 배포 차단을 분리한다.

우선순위는 다음과 같다.

1. **최신 작업 보존·규칙의 정확성·진행 불가 방지.**
2. **예쁜 기본 도트와 명확한 실제 액션.** 보기 싫은 기본 캐릭터에 프레임만 추가하지 않는다.
3. **일관된 자동전투.** 이유 없이 서 있기·왕복하기·추격하다 공성 포기하기를 줄인다.
4. **30명 환경의 안정성과 학생 입력 응답성.**
5. **실제 배포·버전 식별·외부 접속 확인.**

## 2. 사실, 고정 규칙, 제안값의 구분

문서의 `[고정]`은 사용자가 명시한 요구, `[현행]`은 조회한 원격 코드에 존재하는 값, `[제안]`은 이번 구현을 위한 초기 정책, `[검증필요]`는 실제 실행으로 확인해야 할 항목이다.

### 2.2 현재 구현을 먼저 유지하는 항목

다음은 사용자 원문 자체가 아니라 **조회한 코드의 기준값**이다. 로컬 작업이 더 최신이면 비교·기록 후 최신 정상 동작을 우선한다.

- 정답 1원, 오답 0원. 시작 무료 일반 영웅 선택 1회. 처치 골드 0.
- 일반 80/20/0%, 고급 30/60/10%. 등급 순서는 일반/고급/전설.
- 일반 뽑기 역할군: 전체·탱커·근접·원거리·마법·지원. 고급: 전체·탱커·근접·마법. 전설이 없는 역할군의 10%를 임의 재분배하지 않는다.
- 중복 영웅은 독립 인스턴스. 창고 120칸. 꽉 차면 결제 전에 거절.
- Lv.5, Lv.2·Lv.5 스킬 해금. 레벨업 비용 2/3/4/6원. 위력+생명 강화 합계 3회, 비용 2/4/6원.
- 사망 후 재출정 최소 대기 **20초**. 과거 명세의 5초로 조용히 되돌리지 않는다. 이후 튜닝 시 변경 사유·동일 규칙 적용·완주 결과를 남긴다.
- 웨이브 간격 20초. 1웨이브 전체 28기, 영웅 30명과 합하면 58기. 2웨이브가 모두 살아 있으면 86기. 구조물·투사체·지속 효과는 별도다.
- 월드 1536×768, 기본 라인 폭 144, 합류 폭 240. 지도 좌표를 바꾸면 길찾기·충돌·사거리·카메라·테스트를 함께 갱신한다.
- 외곽/내곽/수호/넥서스 HP는 9000/12000/9000/12000. 현재 후반 미니언 구조물 피해 배율은 0/480/600/720초에 1/2/8/16배다. 이 가파른 배율은 **재검토 대상이지 원작의 규칙이나 사용자 확정값이 아니다**.
- 원격 보고서에 목표 경기 길이와 서버 틱 성능 미달이 남아 있다. 새 버전이 기존 시험 통과를 자동 상속한다고 보고하지 않는다.

## 3. 시작 전: 로컬 리워크 보존이 첫 번째 작업이다

조회한 main은 `d060b535c49b63d219f851c431e0294e9dbcb157`이다. 사용자는 그 이후 Codex에서 아트를 대략 리워크했다고 했으므로 원격 main이 최종 아트라고 가정하지 않는다.

### 3.1 변경 전에 작성할 BASELINE_AUDIT.md

- 현재 경로, 저장소 remote, branch, HEAD, git status, worktree 목록을 기록한다.
- 추적/미추적 변경, 스프라이트 PNG/JSON, 원본 작업 파일, 생성·패킹 스크립트를 목록화한다.
- 현재 스프라이트·메타데이터·스타일 파일에 SHA-256을 기록하고 안전한 체크포인트 커밋 또는 작업 백업을 만든다. 개인키·실제 DB·.env·학생 데이터는 커밋하지 않는다.
- 원격과 로컬의 차이를 확인한 뒤 새 작업 브랜치를 만든다. `reset --hard`, `git clean -fd`, 무단 force-push, 무조건적인 main checkout은 금지한다.
- 현재 게임을 실행하여 영웅 갤러리·실제 호스트 전투·학생 전투·정비 화면을 캡처한다. 스프라이트 시트만 보고 완료를 판단하지 않는다.
- 사용자가 이미 개선한 결과는 폐기하지 말고 후보 기준으로 삼는다. 어떤 자산을 유지·수정·교체했는지 자산별로 기록한다.

### 3.2 오래된 도트 재생성 방지

원격 `package.json`의 build 첫 단계는 `node scripts/build-sprites.mjs`다. `npm test`도 pretest로 build를 호출한다. **최신 PNG만 바꿔 놓고 이 경로를 유지하면 새 그림이 재생성 결과로 덮어써질 수 있다.**

이번 작업은 아래처럼 원본과 파생물을 구분한다.

- 원본: 승인된 PNG 프레임/편집 소스/팔레트/방향별 포즈/메타데이터.
- 파생물: 아틀라스, 압축본, 프레임 인덱스, manifest.
- 일반 build는 **원본을 읽고 검증·패킹만** 한다. 얼굴과 몸을 새로 합성하거나 원본 디렉터리에 쓰지 않는다.
- 기존 생성기는 필요하면 legacy 폴더에 보존하되 기본 build/test에서 호출하지 않는다.
- 빌드 전후 원본 파일 해시가 같다는 시험을 추가한다. 깨끗한 clone에서도 동일한 아틀라스가 만들어져야 한다.

## 4. 팀파이트 매니저 2에서 무엇을 참고하는가

공식 소개의 MOBA형 자동전투, 역할의 조합, 공식 패치에 언급된 전투 합류·후퇴·공성 판단과 정보 구조를 참고한다. 이 문서의 AI 수식과 수치는 **Class Clash용 제안**이다. 원작 내부 코드·프레임 수·비공개 알고리즘을 분석했다고 쓰지 않는다. 공식 자료와 사용자 제공 이미지는 `07_SOURCES_BASELINE.md`를 따른다.

| 참고할 목표 | Class Clash 적용 | 도입하지 않을 것 |

| 작은 영웅도 직업이 읽히는 도트 | 얼굴·비율·무기·색·동작의 일관성 | 원작 얼굴/스프라이트 무단 추출 |

| 상황에 맞는 스킬 | 실제 위협·효과·착지 공간 평가 | 무조건 쿨마다 발사, 무조건 전 스킬 동시 사용 |

## 5. 전체 상태 흐름

### 5.1 방 상태

`LOBBY → OPENING_QUIZ → INITIAL_MAINTENANCE → COUNTDOWN → BATTLE → RESULT → LOBBY(new matchId)`

현재 상태명이 다르면 기존 명칭을 유지하며 대응표를 작성한다. 외부 API 이름 변경은 이번 리워크의 목적이 아니다. 호스트 일시정지는 별도 상태/플래그로 처리하며 재개 명령은 계속 받을 수 있어야 한다. 호스트 취소는 `CANCELLED`, 실제 승리로 기록하지 않는다.

### 5.2 학생 상태와 퀴즈는 서로 독립

학생 생명 주기: `FIRST_PREPARATION → DEPLOYING → ACTIVE → DEAD_MAINTENANCE → DEPLOYING`.
퀴즈: `AVAILABLE → IN_PROGRESS → COOLDOWN → AVAILABLE`.

영웅이 죽어도 퀴즈의 현재 문제·답안·보상·쿨타임을 바꾸지 않는다. 정비 창으로 이동했다가 다시 문제를 이어 풀 수 있다. 탭 새로고침이나 소켓 재연결을 새 퀴즈 시도로 취급하지 않는다.

출정 중 허용: 관전, 문제 응답, 정비 안내·창고의 읽기 전용 정보 보기. 금지: 뽑기, 레벨업, 강화, 활성 영웅 교체, 출정 라인 변경, 다음 출정 확정 예약, 움직임·표적·스킬 명령. UI 비활성화와 서버 검사를 모두 구현한다.

### 5.3 정비 거래와 출정

정비 화면은 보유 영웅 선택, 현재 성장과 비용, 역할 구성, 상/하 라인 선택, 명확한 출정 버튼을 제공한다. 구매/성장 ACK 전에 지갑을 임의로 확정 변경하지 않는다. 출정 처리 시 서버가 상태·잔액 처리 완료·선택 인스턴스·라인·최소 사망 대기·활성 영웅 수를 함께 검증한다.

스킬 준비 시각은 소유 영웅 인스턴스와 기존 공통 쿨타임 정책을 보존한다. 같은 영웅 복사본을 교대시켜 긴 스킬을 초기화하지 못한다. 동시에 도착한 구매와 출정은 순서화하고, 출정 후 도착한 성장 요청은 거절한다.

## 6. 게임 전체의 시각 방향

전장은 어두운 덩어리나 혼잡한 장식으로 채우지 않는다. 차분한 지형, 밝게 구분되는 길, 명확한 양 진영 건물, 서로 다른 영웅 실루엣, 필요한 순간의 선명한 효과를 사용한다. 전체를 똑같이 밝고 화려하게 만들지 않는다.

영웅은 정지 상태부터 보기 좋아야 한다. 미니언은 영웅보다 작고 단순하지만 걸음·공격·피격이 연결되어야 한다. UI는 직업별 초상과 역할·등급·레벨·두 스킬 정보를 일관되게 사용한다. 한글 문제 본문은 읽기 좋은 글꼴로 충분한 크기를 확보한다.

그래픽 자세한 기준은 02, 18명별 방향은 06을 따른다.

## 7. 구현 단계와 완료 게이트

### G0 — 보존·기준 실행

최신 로컬 변경 보존, 실제 원본 경로 및 build 덮어쓰기 검사, 기존 테스트 재현, 현재 게임 캡처. 실패한 기준 테스트도 숨기지 않는다.

### G1 — 아트 기준과 렌더링 경로

성전사·궁수·화염술사의 기존 개선본을 비교하고 필요한 수정을 한다. 정지 기본 자세, 방향 일관성, 걷기, 평타, 두 스킬, 피격·사망을 실제 게임에서 확인한다. 이 기준으로 미니언과 구조물 스타일을 맞춘다. 미적 승인을 자동시험 PASS로 대체하지 않는다. 사용자의 명시 승인 없이 `USER_APPROVED`라고 기록하지 않는다.

### G2 — 매치엔진

미니언 이동→근접 자리→원거리 거리 유지→지원 스킬→포탑 진입→넥서스 마무리 순서로 회귀 비교한다. 한 번에 수치와 AI와 사거리를 전부 바꿔 원인을 알 수 없게 만들지 않는다.

### G3 — 전체 18명·전장·VFX·UI

검증된 방식으로 남은 영웅과 스킬을 연결하고, 실제 30영웅 교전과 학생 퀴즈·정비 UX를 통합한다. 3명 샘플만 만든 것을 전체 작업 완료로 보고하지 않는다.

### G4 — 동기화·성능·밸런스

독립 30클라이언트·1배속 렌더링·재접속·재경기·고정 시드 완주를 각각 측정한다. 늦은 스냅샷·DB 지연·이펙트 유실을 따로 관찰한다.

### G5 — GitHub·공개 배포

검증한 커밋을 push하고 PR/배포 상태를 보고한다. 권한이 있는 환경에서 HTTPS/WSS·영구 저장소·외부 접속 시험을 완료한 뒤 실제 공개 주소를 제출한다. 배포 자격 증명이 없으면 구현을 계속 완료하고 정확한 미충족 항목을 보고한다.

중간에 사람이 승인해야 하는 시점은 별도 표시하되, 그동안 독립적인 엔진·시험·배포 설정 작업은 계속한다. 모든 항목을 “나중에”로 미루는 계획서만 제출하지 않는다.

## 8. 작업 범위에서 제외하는 변경

새 결제·현금 재화, 계정 회원가입, 가챠 천장·새 등급, 3~4팀, 플레이어 직접 조작, 생존 중 성장, 무한 후퇴·본진 자동 회복, 캐릭터 영구 계정 육성, 여러 게임의 통합 서버로의 대규모 이관, 엔진 언어 교체, Unity 재개발은 이번 작업에 넣지 않는다.

이미 정상인 경제 원장·퀴즈 검증·세션·재접속 로직을 시각 리워크 때문에 갈아엎지 않는다. 다만 **이번에는 전투 AI와 렌더링 개선이 명시된 범위**이므로, 과거 “AI를 전혀 수정하지 말라”는 아트 전용 요청을 이유로 매치엔진을 방치하지 않는다.
